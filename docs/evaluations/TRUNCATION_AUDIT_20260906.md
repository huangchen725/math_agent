## 2. 首要原因链：参数省略改变了实际请求

从四个 Git 提交提取真实 `_chat` / `_solve_plain` 方法，以本地保存的官方公开 baseline client 组装 HTTP 请求；HTTP 完全替换为 fixture，使用虚构凭据，零网络调用。三种 client 默认值下的观察如下：

| Agent 版本 | client 未配置思考 | client 默认 False | client 默认 True |
| --- | --- | --- | --- |
| R0 `ba63ac0` | 请求明确 False | False | 请求覆盖为 False |
| `c009929` | 请求省略参数 | False | True |
| `9126c04` | 请求省略参数 | False | True |
| `6d42d2c` | 请求省略参数 | False | True |

各次生成请求的 max_tokens 都是 8192。因此已证实的是：**三参数投影改变了对 client / 服务端默认值的依赖，不能叫作求解行为已证明不变。** 这不是“R0 单独导致退化”，也不是已经证实“全部由 R1 导致”。

[书生普通 Chat API 文档](https://internlm.intern-ai.org.cn/doc/docs/Chat/)于 2026-09-06 核验，397B 默认开启深度思考。若本批次模型为 397B，且 client 没有显式关闭思考，旧的短预算就可能在形成最终答案前耗尽。若 client 默认 False，则不能使用这一解释，必须继续检查模型变化、平台有效输出上限、实际长生成需求或上下文限制。**这是有代码和官方文档支持的首要假设；实际批次根因仍缺真实请求证据。**

当前各阶段默认上限：生成/反思 8192，验证/批评 1024，兜底 512。要求“只输出答案”是提示词，不等于关闭模型内部思考；缩短兜底预算不保证更快拿到结论。重做一次短预算求解也不等于续写先前推导。

本次每请求输出 token 从约 1091 升到 4204，总输出占比升至 90.32%，与“输出更长且大量未完成”相容，但不能从 token 汇总反推出 reasoning token 的实际占比。生成、验证、批评和兜底分别占多少截断同样未知。

## 6. 按结果选择应对措施

1. **确定性修复先行**：下一修复提交首先解决 TRUNC-02 和 TRUNC-04，加入会在旧版失败的永久回归，保持三参数接口、导入隔离和 trace 白名单。合格候选保留与未合格内容失败关闭须同时成立。
2. **若省略时 length、False 时完整**：支持思考模式与短预算不匹配。正式注入 client 没有保证第四参数，不能直接恢复 thinking_mode=False；优先在三参数内验证更合适的输出预算和较少短验证请求。普通 API 的开关实验用于定位，不自动成为正式补丁。
3. **若增大预算后完整且模型/条件一致**：按阶段选预算，不全局无差别加大；监测 completion_tokens 是否仍停在同一固定值，以识别可能的平台上限。先只改预算，再独立比较候选数量或 verifier 策略，避免无法归因。
4. **若 False 和加预算都无改善**：检查原始 content 是否为空、reasoning 是否单独返回、模型回执、HTTP 状态、上下文长度与实际耗时。不得继续靠添加中文答案标签、放宽 parser 或吞异常制造有效答案。
5. **保留并收束而非重复短重算**：有完整候选时优先交付；确需恢复时只基于允许使用的可见文本，在单题剩余预算内做一次有明确上限的恢复。不能假定不可见 reasoning 可续写，不能无限续写或反复 512-token 重算。
6. **小诊断后再做代表性配对测试**：两题只能验证机制，不能据此证明 112 题收益。筛出条件后用开发集扩展，最后一次独立留出验收；同时比较正确率、无效率、截断率和耗时，不能只追求没有 invalid。
7. **发布验收分开**：工程门禁、新反例、真实模型表现、正式运行各自留证。当前即便 384 项绿灯仍为专项不通过；每日正式候选必须冻结实际提交并核对远端和抓取 SHA。

## 8. 后续补查：8192 口径与服务端 120 秒中断

用户随后提示“好像说模型单次截断是8192”。此为待核验线索，尚无对应原文或适用批次。当前代码主动设置生成/反思 max_tokens=8192 是确定事实；公开 baseline README 只说明平台可能限制 max_tokens，没有明确写 8192。不能把本地设置直接认定为模型或正式平台硬上限。

重新逐节核验 [Chat 文档的调用参数说明](https://internlm.intern-ai.org.cn/doc/docs/Chat/)发现此前审计遗漏：普通 API 文档说明模型在 120 秒内未完成时，接口会中断输出并返回已有结果。这与本地 requests.timeout=120、Agent 600 秒软期限及 runner 1200 秒单题硬期限是不同层次。本文前述原因链须补充**服务端时间中断**这一独立候选原因；目前没有证据确定它在本批次如何执行或如何记入 truncated_count。

后续诊断已有 elapsed_ms、finish_reason、completion_tokens 和请求上限字段，可用于检查：若返回 length 且 token 接近请求上限，支持 token 限制；若 token 明显低于上限、耗时集中在约 120 秒且增大上限无改善，则优先调查时间中断。该时间关联本身仍不是唯一根因证明，需要区分传输超时、服务端返回和平台调度。服务端时间限制不能通过延长本地 HTTP 等待解决。

计划中的 16384 条件仅为普通 API 上限敏感性探针，不是正式可用额度或修复承诺。若取得正式 8192 硬上限原文，应据其适用范围调整计划，不把超出上限作为正式方案。正式应对须能在已有上限内工作：保留已完成候选、降低无效验证/反思消耗、控制每次任务范围，并只在允许的剩余预算内进行有界恢复。本次未执行真实 API，原冻结计划没有被静默改写。
