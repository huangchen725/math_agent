## 不可触碰的边界

1. 不得由人工对评测题逐题选择、改写或补充答案。
2. 不得在评测结束后补填结果，也不得把人工创建的 checkpoint 当成模型输出。
3. 不得伪造、拼接或改写运行日志。正式提交的日志和结果必须来自同一次自动运行并保留原始文件哈希。
4. 不得用未经允许的外部闭源服务代答。运行时只允许赛事官方注入客户端、官方 Intern API 和本地受限 SymPy 工具。
5. 正式模型必须属于当前书面证据覆盖的 allowlist，并与提交页实际选择及留存回执一致；不得把群内“397/35B”简写自行映射成 API 模型 ID。
6. 每题必须返回可解析 JSON，包含非空 `final_response` 和列表 `trace`；最终文本必须以唯一的非空 `最终答案：...` 行结束。
7. 公开 `trace`、标准输出和标准错误不得作为隐藏题或模型交互回传通道；题面、prompt、模型/候选/verifier/critic/tool 正文、最终答案、异常消息和敏感字段不得进入 trace。

违反前四项属于资格风险，不能用更高正确率、人工复核或赛后说明抵消。第五、六项属于项目正式验收阻断项；allowlist 只表示当前书面证据覆盖范围，不代表登录后提交页或实际运行模型已被本地代码证明。

## 官方契约缺口的处理原则

官方材料尚未完整定义注入 client、响应类型、模型 ID、请求/token 预算、容器资源、Judge 输入、runner 加载细节和平台变更版本。完整缺口编号见 `OFFICIAL_MATERIALS_REGISTER.md` 的 `OFFICIAL-GAP-*` 矩阵。任何开发者必须遵守：

- 未说明的能力不得作为运行前提；采用最小公开接口和本地预算。
- 官方 baseline 的参考实现不等于平台注入实例的版本保证；不得读取私有字段或靠同名方法猜测能力。
- 线上 0 请求、0 token 只能证明请求前失败，不能只凭聚合日志锁定唯一异常或平台变更日期。
- 新官方答复必须保存原文、日期、来源和 SHA-256；动态网页没有不可变版本时至少保存 URL、核验日期、页面标题/更新时间、关键事实和可用快照，再更新本文件、工程规范、测试和发布 manifest；禁止只在聊天中口头覆盖规则。
- 正式提交前必须逐项核对模型选择页、依赖环境公告、资源限制和 client/runner 更新；没有公告时继续失败关闭。

## 正式运行前

- 使用全新输出目录，不复制、预置或手工创建任何题目结果文件。
- 确认 `COMPETITION_MODE=1`，模型属于 `intern-s1`、`intern-s1-pro`、`intern-s2-preview` 且与本次 AtomGit 页面选择回执完全一致；默认 `intern-s1` 不能替代该回执。
- 确认根入口兼容 `__init__(self, client, *args, **kwargs)` 签名及 `ReasoningAgent(client=official_client)` 调用；未知 client 仍只能收到三个公开 `chat` 参数。
- 确认名为 `atomgit` 的队伍仓库远程已配置、`main` 已同步且作品页已点击“提交作品”。当前仓库只有 GitHub 远程时不得宣称提交链路已就绪。
- 固定干净 commit、输入数据 SHA-256、配置、并发、开始时间和预计请求上限。
- 用隔离入口门禁确认 `user_agent.py` 不依赖 judge 当前目录，并确认无 `**kwargs` 的三参数 injected-client 回归实际调用公开 `chat()`，且每次只收到三个允许参数。
- 运行 `python -m scripts.run_quality_gates`；不得删除 `competition_compliance`、格式或接口检查来换取通过。
- 若主办方或提交页明确其它模型、服务或客户端能力，把原始答复、日期、适用批次与哈希归档，再通过正常代码评审更新证据登记册、本文件和门禁；不得只改环境变量或打包参数。

## 正式运行与留证

- 运行期间不得根据单题内容暂停后改 prompt、切模型、选择候选或重新提交某一道题。
- 基础设施故障只能按事先冻结的全局重试规则处理；规则变更后必须整批重新运行并区分版本。
- 保留平台原始日志、runner 结果、运行摘要和错误记录。不要在原文件上“修正格式”；需要重算统计时生成新文件，并记录输入文件哈希和工具版本。
- 人工盲审只能作为独立评估材料，不能回写模型答案或冒充自动正确率。

## AtomGit 提交与冻结

1. 在 AtomGit 完成报名/组队，在队伍组织下创建仓库，并把它以远程名 `atomgit` 加到现有本地仓库，再推送 `main`；GitHub `origin` 可以保留但不能替代 AtomGit。
2. 在作品页关联正确仓库、选择 allowlist 内的精确模型并点击“提交作品”。只推送代码不会入队。
3. 记录点击时间和预计北京时间 12:00/24:00 批次；从点击提交到平台完成抓取期间冻结 `main`，不要再推送或合并。
4. 抓取后读取 AtomGit 远端 `main` SHA，与本地冻结 SHA 和发布 manifest 对账。平台不接收选手填写 commit hash，但本地仍必须用 SHA 留证。
5. 记录当天和当周提交次数，分别不得超过 2 次和 10 次；不要用重复空提交消耗名额。
6. 初赛截止前把最终代码、`user_agent.py`、运行依赖和说明文件打成 ZIP，按当前技术规则发送到组委会邮箱。说明文件写队伍、题目、AtomGit URL、`main` 和所选模型，不填写平台已取消的 commit-hash 字段；本地 SHA 仅作审计。

## 提交前四眼核对

1. 两人分别确认模型、端点、commit、数据哈希和质量报告一致；个人参赛时至少分两次独立核对并留下时间记录。
2. 对每个提交日志、结果 JSON、技术报告、演示视频和压缩包计算 SHA-256，写入只追加的提交清单。
3. 随机抽查结果 JSON 能解析、字段完整、`final_response` 非空；不得人工修复抽查到的单题，发现问题应修代码后整批重跑。
4. 确认没有 `.env`、token、私有题面、人工答案表、临时补丁或非授权服务配置进入提交包。
5. 抽查公开 `trace` 只有结构化元数据，不含题面、prompt、模型/工具正文、最终答案或异常消息。
6. 用正式命令生成源码包。若 manifest 状态为 `draft`、模型不在 formal allowlist、材料指纹/动态页面核验信息/baseline commit 缺失、质量报告不完整或工作树不干净，停止提交。
7. 核对 `atomgit` 远程、作品页点击回执、模型回执、批次、抓取后的 `main` SHA，以及最终 ZIP 邮件发送/送达记录。缺任一适用证据时不得把 GitHub 推送、AtomGit 单独推送或本地 ZIP 当成已完成正式提交。

## 尚不能由代码证明的事项

离线门禁可以阻止常见误配置并留下可审计证据，但不能证明操作者从未在代码外人工干预，也不能替代主办方对模型、客户端、资源或外部服务的授权。正式提交仍需保存原始平台记录、书面授权和人工操作日志；缺少这些证据时应按未获保证处理。门禁通过也不能把 `OFFICIAL-GAP-*` 自动标记为已解决。
